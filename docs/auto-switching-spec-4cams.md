# ТЗ: автоматическое переключение камер и управление звуком для схемы 4 участника / 4 камеры

## 1. Введение и цель

Цель системы: автоматически формировать видеомонтаж и управлять звуком для формата `1 ведущий + 3 гостя` так, чтобы результат выглядел как работа аккуратного живого режиссёра:

- камера переключается логично и без визуального дёрганья;
- ведущий и гости попадают в кадр в ожидаемые моменты;
- начало реплик не обрезается;
- перебивания и короткие реплики не ломают монтаж;
- одновременная речь обрабатывается предсказуемо;
- задержка перевода камеры 3 учитывается как базовое инженерное ограничение, а не как исключение.

Настоящий документ фиксирует конкретное поведение системы. Все спорные места решены однозначно. Документ предназначен для прямой реализации инженером без дополнительного переписывания требований.

## 2. Состав системы

### 2.1 Участники

- `HOST` — ведущий.
- `GUEST_1` — гость 1.
- `GUEST_2` — гость 2.
- `GUEST_3` — гость 3.

### 2.2 Камеры

- `CAM_1` — общий план всей студии, ведущий + гости.
- `CAM_2` — общий план гостей, без ведущего.
- `CAM_3` — движущийся крупный план гостя.
- `CAM_4` — крупный план ведущего.

### 2.3 Аудиоканалы

Система получает 4 изолированных аудиоканала:

- `MIC_HOST`
- `MIC_GUEST_1`
- `MIC_GUEST_2`
- `MIC_GUEST_3`

Для каждого канала система рассчитывает независимую детекцию речи и итоговый уровень выхода.

### 2.4 Входные события

Система должна опираться на следующие входные события и сигналы:

- аудиофреймы с шагом обработки `10 ms`;
- `speech_prob(participant)` — вероятность речи по VAD;
- `speech_level_db(participant)` — уровень речевой энергии в dBFS;
- `speaker_started(participant)` — подтверждённое начало речи;
- `speaker_stopped(participant)` — подтверждённый конец речи;
- `overlap_started(active_set)` — началась одновременная речь двух и более участников;
- `overlap_stopped()`;
- `silence_started()` — нет подтверждённой речи;
- `cam3_move_started(target_guest)` — камера 3 начала перевод на целевого гостя;
- `cam3_ready(target_guest)` — камера 3 навелась на целевого гостя;
- `cam3_timeout(target_guest)` — перевод камеры 3 не завершён за допустимое время;
- `manual_override` — ручное управление оператором или режиссёром; out of scope для MVP, но интерфейс события должен быть предусмотрен.

## 3. Явные инженерные допущения

### 3.1 Архитектурные допущения

- Система работает в режиме автоматического режиссирования с допустимой задержкой звука на выходе до `300 ms`.
- Видео переключается без искусственного общего буфера; исключение — учёт состояния перевода камеры 3.
- Камера 3 умеет принимать команду `target_guest = {1|2|3}` и возвращать состояние `MOVING` / `READY`.
- Система знает, на какого гостя в данный момент наведена камера 3.
- Между гостями на площадке есть достаточное различие по аудиоканалам, чтобы VAD + уровень + относительное доминирование могли отделять реальную речь от протечки.

### 3.2 Монтажные допущения

- Если говорит ведущий один, предпочтительный кадр — `CAM_4`.
- Если говорит один гость, предпочтительный кадр — `CAM_3`, но только если она уже готова или успеет подготовиться без потери логики монтажа.
- Если одновременно говорят два или более гостя, предпочтительный кадр — `CAM_2`.
- Если одновременно говорит ведущий и хотя бы один гость, предпочтительный кадр — `CAM_1`.
- Пока камера 3 переводится, в эфир нельзя выводить неподготовленный или движущийся кадр с неё.

### 3.3 Аудиодопущения

- Для предотвращения обрезания начала реплик система хранит `audio_pre_roll_buffer = 300 ms` на каждый микрофон.
- По умолчанию система применяет не мгновенный hard mute, а двухступенчатое ослабление:
  - быстрая стадия attenuation;
  - hard mute только после устойчивой неактивности.
- При overlap допускается наличие более одного активного микрофона одновременно.

## 4. Логика определения активного говорящего

### 4.1 Общий принцип

Определение активного говорящего выполняется по каждому участнику независимо и состоит из четырёх слоёв:

1. `VAD`: вероятность речи.
2. `Speech band level`: энергия в речевом диапазоне `200-4000 Hz`.
3. `Relative dominance`: сравнение уровня и вероятности речи между участниками.
4. `State stabilization`: attack / release / hold / hysteresis.

### 4.2 Базовые правила активации

Участник считается `ACTIVE`, если одновременно выполнены условия:

- `speech_prob >= 0.65`
- `speech_level_db >= -27 dBFS`
- условия держатся не менее `120 ms`

Участник может быть активирован ускоренно, если выполнены условия:

- `speech_prob >= 0.82`
- `speech_level_db >= -24 dBFS`
- условия держатся не менее `60 ms`

Это ускоренное правило нужно, чтобы не терять резкие начала коротких вопросов и перебивок.

### 4.3 Правила деактивации

Участник перестаёт считаться `ACTIVE`, если:

- `speech_prob < 0.45`
- `speech_level_db < -31 dBFS`
- состояние держится не менее `release = 220 ms`

После деактивации действует `hold = 350 ms`: участник сохраняет статус `RECENTLY_ACTIVE`, чтобы система не дёргалась на микропаузах внутри фразы.

### 4.4 Hysteresis

Используется гистерезис между включением и выключением:

- порог включения: `-27 dBFS`
- порог выключения: `-31 dBFS`

Разрыв `4 dB` обязателен. Реализация без гистерезиса считается некорректной.

### 4.5 Relative dominance и подавление протечки

Если активны два и более канала, система должна определить, это:

- реальная одновременная речь;
- или протечка одного спикера в чужой микрофон.

Правило:

- если один канал громче другого минимум на `6 dB`, а `speech_prob` у более тихого канала ниже минимум на `0.12`, более тихий канал трактуется как `BLEED`, а не как отдельная речь;
- если разница меньше, оба канала считаются реальной одновременной речью;
- для группы гостей правило применяется попарно, затем собирается итоговый активный набор.

### 4.6 Выходной набор speech states

После агрегации система обязана выдавать одно из состояний:

- `SILENCE`
- `HOST_ONLY`
- `GUEST_1_ONLY`
- `GUEST_2_ONLY`
- `GUEST_3_ONLY`
- `HOST_PLUS_GUEST`
- `MULTI_GUEST`
- `GROUP_OVERLAP`

Где:

- `HOST_PLUS_GUEST` — одновременно активен ведущий и хотя бы один гость;
- `MULTI_GUEST` — одновременно активны два или более гостя, ведущий молчит;
- `GROUP_OVERLAP` — активны ведущий и минимум два гостя одновременно.

## 5. Логика выбора камеры

### 5.1 Общий приоритет

При выборе камеры действует следующий приоритет сверху вниз:

1. Состояния overlap.
2. Безопасные планы на время перевода камеры 3.
3. Устойчивый крупный план текущего спикера.
4. Периодический re-establishing shot.
5. Удержание текущего кадра по антидребезгу.

### 5.2 Когда использовать камеру 1

`CAM_1` должна использоваться в случаях:

- `HOST_PLUS_GUEST`;
- `GROUP_OVERLAP`;
- пауза дольше `silence_timeout`;
- re-establishing shot после длинного быстрого обмена репликами, если за последние `25 s` не было общего плана всей студии;
- fallback, если состояние неоднозначно и `CAM_2` не покрывает всех активных участников.

`CAM_1` не должна использоваться как основной кадр для одиночного гостя или одиночного ведущего, кроме случая принудительного safe fallback.

### 5.3 Когда использовать камеру 2

`CAM_2` должна использоваться в случаях:

- говорит один гость, но `CAM_3` ещё не готова;
- говорят два или более гостя одновременно;
- быстрый обмен репликами между несколькими гостями, когда ожидание `CAM_3` не даёт практической пользы;
- камера 3 переведена не на того гостя, а текущий гость говорит слишком коротко, чтобы имело смысл ждать новый перевод.

`CAM_2` является основным безопасным кадром для гостевого блока.

### 5.4 Когда использовать камеру 3

`CAM_3` должна использоваться только при выполнении всех условий:

- активен ровно один гость;
- этот гость подтверждён как dominant speaker;
- камера 3 уже наведена на него либо перевод завершится в пределах `cam3_wait_timeout = 2.0 s`;
- ожидаемая полезная длительность крупного плана после завершения перевода не менее `600 ms`.

Практическое правило переключения:

- при начале устойчивой речи гостя система немедленно запускает перевод `CAM_3` на этого гостя;
- пока идёт перевод, в эфире остаётся `CAM_2`;
- после получения `cam3_ready(target_guest)` система переключает эфир на `CAM_3`, только если тот же гость всё ещё активен или находится в состоянии `RECENTLY_ACTIVE` не более `200 ms`;
- если гость уже замолчал или произошёл overlap, `CAM_3` в эфир не выводится.

### 5.5 Когда использовать камеру 4

`CAM_4` должна использоваться в случаях:

- `HOST_ONLY`;
- быстрый обмен `HOST ↔ GUEST`, когда говорит ведущий и предыдущий кадр был гостевым;
- возврат с `CAM_1` или `CAM_2` на ведущего после завершения перебивания.

`CAM_4` является основным портретным кадром ведущего и должна иметь приоритет над `CAM_1`, если ведущий снова стал единственным активным спикером.

## 6. Работа с задержкой камеры 3

### 6.1 Что показывать, пока камера переводится

Пока `CAM_3` переводится:

- если говорит один гость — показывать `CAM_2`;
- если ведущий перебивает гостя — показывать `CAM_1`;
- если ведущий снова стал единственным спикером — немедленно возвращаться на `CAM_4`;
- если одновременно говорят несколько гостей — оставаться на `CAM_2`.

Показывать moving-shot с `CAM_3` запрещено.

### 6.2 Когда ждать камеру 3 имеет смысл

Ждать `CAM_3` имеет смысл, только если:

- активный гость удерживает доминирование минимум `500 ms`;
- до этого не было более `2` смен активного гостя за последние `3 s`;
- текущее состояние не overlap;
- суммарная длительность гостевой реплики, вероятно, превысит `2.6 s`.

Практическая реализация прогноза:

- если гость говорит уже `>= 700 ms` и за это время не произошло смены доминирующего участника, система считает реплику потенциально длинной;
- в этот момент перевод `CAM_3` считается оправданным;
- если к завершению перевода гость уже замолчал, эфирный cut на `CAM_3` отменяется.

### 6.3 Когда не нужно переключаться на камеру 3 вообще

На `CAM_3` не нужно переключаться, если:

- реплика гостя короче `2.0 s` и уже почти завершилась;
- говорят несколько гостей;
- ведущий активно перебивает гостя;
- за последние `4 s` было более `3` смен активного спикера;
- `CAM_3` ещё едет, а текущий гость уже перестал быть dominant speaker;
- до конца допустимого окна остаётся менее `600 ms`.

В этих случаях система обязана оставаться на `CAM_2` или `CAM_1` в зависимости от активного набора участников.

### 6.4 Как не опаздывать с её выводом в эфир

Чтобы `CAM_3` не выходила в эфир слишком поздно, система должна:

- запускать перевод сразу при подтверждении состояния `single guest speaker`;
- не ждать полного `shot_hold_time`, если текущий эфирный кадр — безопасный гостевой `CAM_2` и `CAM_3` только что стала `READY`;
- иметь отдельный `cam3_cut_in_grace = 150 ms`: если камера 3 стала готова и тот же гость активен, переключение допускается до истечения общего cooldown;
- отменять cut на `CAM_3`, если гость замолчал более чем на `200 ms` до завершения перевода.

## 7. Логика управления звуком

### 7.1 Общий принцип

Управление звуком строится по модели `active / recently_active / inactive`.

Каждому участнику назначается один из трёх уровней:

- `0 dB` — активный говорящий;
- `-9 dB` — недавно активный или потенциально возвращающийся спикер;
- `-18 dB` — неактивный участник;

Дополнительно допускается hard mute:

- `-96 dB` — если участник неактивен более `2.0 s` и не находится в overlap-сценарии.

### 7.2 Mute / unmute / attenuation

Реализация должна использовать:

- `audio attack = 70 ms`
- `audio release = 180 ms`
- `audio hold = 350 ms`
- `audio_pre_roll = 300 ms`
- `audio_post_roll = 120 ms`

Правила:

- при открытии канала используется pre-roll;
- при закрытии канала сначала применяется attenuation, затем hard mute;
- мгновенное переключение `0 dB -> -96 dB` без промежуточной attenuation запрещено.

### 7.3 Поведение для ведущего

Если активен только ведущий:

- `MIC_HOST = 0 dB`
- все гости: `-18 dB`
- гости, неактивные более `2.0 s`: `-96 dB`

Если ведущий в перебивке с гостем:

- `MIC_HOST = 0 dB`
- активный гость = `0 dB`
- остальные гости = `-18 dB`

### 7.4 Поведение для активного гостя

Если активен ровно один гость:

- его микрофон = `0 dB`
- ведущий = `-18 dB`, если молчит;
- ведущий = `-9 dB`, если только что закончил реплику и находится в `RECENTLY_ACTIVE`;
- остальные гости = `-18 dB` или `-96 dB` по таймауту устойчивой неактивности.

### 7.5 Поведение для молчащих гостей

Для молчащих гостей действует правило:

- первые `350 ms` после конца их речи — `-9 dB`;
- далее до `2.0 s` — `-18 dB`;
- после `2.0 s` — `-96 dB`.

Это правило необходимо, чтобы не резать дыхание и микроответы на стыках реплик.

### 7.6 Поведение при перебиваниях и одновременной речи

Если одновременно говорят ведущий и гость:

- оба канала = `0 dB`;
- остальные гости = `-18 dB`.

Если одновременно говорят два или более гостя:

- все подтверждённо активные гости = `0 dB`;
- ведущий = `-18 dB`, если молчит;
- неактивные гости = `-18 dB`.

Если overlap распознан как bleed, а не как реальная вторая речь:

- доминирующий говорящий = `0 dB`;
- bleed-канал = `-18 dB` или `-96 dB` по общему правилу.

## 8. Антидребезг и стабилизация

### 8.1 Minimum shot hold time

Минимальное удержание любого кадра:

- `shot_hold_time = 1.2 s`

Исключения:

- переход в `CAM_1` при явном overlap можно делать раньше, начиная с `0.8 s`;
- переход в `CAM_4` на ведущего после safe-plan допускается при `0.7 s`, если ведущий стал единственным спикером;
- выход `CAM_3` в эфир после завершения перевода допускается по `cam3_cut_in_grace`, даже если глобальный cooldown ещё не истёк.

### 8.2 Cooldown

Глобальный cooldown между соседними видеопереключениями:

- `cooldown = 700 ms`

Отдельный cooldown для re-establishing wide:

- `wide_reestablish_cooldown = 25 s`

Отдельный cooldown для повторного вывода `CAM_3`:

- `cam3_reuse_cooldown = 1.0 s`

### 8.3 Hysteresis

По речи используется обязательный гистерезис:

- activation threshold: `-27 dBFS`
- release threshold: `-31 dBFS`

По видео используется обязательный гистерезис состояний:

- новое состояние должно удержаться минимум `180 ms`, прежде чем разрешён cut;
- для overlap-состояний — `120 ms`;
- для silence-состояния — `400 ms`.

### 8.4 Speech debounce

Рекомендуемое стартовое значение:

- `speech debounce = 120 ms`

Назначение:

- отбрасывать одиночные всплески;
- не пропускать короткие слова и короткие вопросы.

### 8.5 Silence timeout

Рекомендуемое стартовое значение:

- `silence_timeout = 800 ms`

Правило:

- если нет подтверждённой речи дольше `800 ms`, система переводит видео на `CAM_1`;
- звук не должен мгновенно hard-mute всех участников; сначала все каналы должны находиться на `-18 dB` минимум `300 ms`.

| Говорят ведущий и несколько гостей | `GROUP_OVERLAP` | `CAM_1` | Все активные = `0 dB` | Только общий план корректен |
| Пауза | `SILENCE >= 800 ms` | `CAM_1` | Все каналы постепенно к `-18 dB`, потом `-96 dB` | Безопасный мастер на паузе |
| `CAM_3` ещё едет | `cam3_state=MOVING`, говорит один гость | `CAM_2` | Гость открыт, остальные attenuate | Запрещено выводить moving-shot |
| `CAM_3` не успела, гость замолчал | `cam3_ready`, но target уже inactive | Сохранить текущий safe-plan | По состоянию активных каналов | Переключение на `CAM_3` отменяется |
| Длинный диалог без общего плана | нет `CAM_1` более `25 s`, активный обмен | `CAM_1` на `1.5-2.0 s` | Без изменений по активным каналам | Re-establishing shot |
| Протечка в чужом микрофоне | `delta >= 6 dB`, более тихий канал слабее по VAD | Камера по доминирующему говорящему | Доминирующий `0 dB`, bleed attenuate | Не считать bleed отдельной речью |

## 10. State machine

### 10.1 Перечень состояний

Система должна иметь следующие верхнеуровневые состояния видеорежиссуры:

- `STATE_IDLE_WIDE`
- `STATE_HOST_FOCUS`
- `STATE_GUEST_SAFE`
- `STATE_GUEST_CLOSE`
- `STATE_MULTI_GUEST`
- `STATE_HOST_GUEST_OVERLAP`
- `STATE_GROUP_OVERLAP`
- `STATE_CAM3_MOVING`

Отдельно должна вестись внутренняя подмашина состояния камеры 3:

- `CAM3_IDLE`
- `CAM3_MOVING_TO_GUEST_1`
- `CAM3_MOVING_TO_GUEST_2`
- `CAM3_MOVING_TO_GUEST_3`
- `CAM3_READY_ON_GUEST_1`
- `CAM3_READY_ON_GUEST_2`
- `CAM3_READY_ON_GUEST_3`

### 10.2 Условия входа

- `STATE_IDLE_WIDE` — `SILENCE >= 800 ms` либо старт программы.
- `STATE_HOST_FOCUS` — `HOST_ONLY`.
- `STATE_GUEST_SAFE` — `GUEST_X_ONLY`, но `CAM_3` не готова или нецелесообразна.
- `STATE_GUEST_CLOSE` — `GUEST_X_ONLY` и `CAM_3 READY on X`.
- `STATE_MULTI_GUEST` — `MULTI_GUEST`.
- `STATE_HOST_GUEST_OVERLAP` — `HOST_PLUS_GUEST`.
- `STATE_GROUP_OVERLAP` — `GROUP_OVERLAP`.
- `STATE_CAM3_MOVING` — старт перевода `CAM_3` при одиночном активном госте.

### 10.3 Условия выхода

- Из `STATE_HOST_FOCUS` выход при появлении гостя, паузе или overlap.
- Из `STATE_GUEST_SAFE` выход:
  - в `STATE_GUEST_CLOSE`, если `CAM_3 READY on current_guest`;
  - в `STATE_MULTI_GUEST`, если появился второй гость;
  - в `STATE_HOST_GUEST_OVERLAP`, если подключился ведущий;
  - в `STATE_IDLE_WIDE`, если наступила пауза.
- Из `STATE_GUEST_CLOSE` выход:
  - в `STATE_MULTI_GUEST`, если появился второй гость;
  - в `STATE_HOST_GUEST_OVERLAP`, если подключился ведущий;
  - в `STATE_HOST_FOCUS`, если заговорил только ведущий;
  - в `STATE_IDLE_WIDE`, если наступила пауза.
- Из overlap-состояний выход при возвращении к одиночному спикеру или паузе.

### 10.4 Приоритеты переходов

Приоритет переходов фиксируется в следующем порядке:

1. `GROUP_OVERLAP`
2. `HOST_PLUS_GUEST`
3. `MULTI_GUEST`
4. `HOST_ONLY`
5. `GUEST_X_ONLY with CAM3_READY`
6. `GUEST_X_ONLY with CAM3_MOVING or CAM3_NOT_READY`
7. `SILENCE`

Если одновременно выполняются несколько условий, используется состояние с более высоким приоритетом.

## 11. Псевдокод основного цикла

```python
FRAME_MS = 10

while True:
    frame = read_next_audio_frame()
    update_audio_buffers(frame)

    for participant in participants:
        vad_prob[participant] = calc_vad(participant, frame)
        speech_db[participant] = calc_speech_band_db(participant, frame)
        raw_active[participant] = detect_active(
            vad_prob=vad_prob[participant],
            speech_db=speech_db[participant],
            attack_ms=120,
            fast_attack_ms=60,
            release_ms=220,
            hold_ms=350,
            activation_db=-27,
            release_db=-31,
        )

    active_set = suppress_bleed_and_build_active_set(raw_active, vad_prob, speech_db)
    speech_state = classify_state(active_set)

    dominant_guest = choose_dominant_guest(active_set, vad_prob, speech_db)

    if speech_state == GUEST_X_ONLY and dominant_guest is not None:
        if cam3.target != dominant_guest and cam3.state not moving_to(dominant_guest):
            cam3.start_move(dominant_guest)

    if speech_state == HOST_ONLY:
        target_video_state = STATE_HOST_FOCUS
    elif speech_state == GUEST_X_ONLY:
        if cam3.is_ready_for(dominant_guest):
            target_video_state = STATE_GUEST_CLOSE
        else:
            target_video_state = STATE_GUEST_SAFE
    elif speech_state == MULTI_GUEST:
        target_video_state = STATE_MULTI_GUEST
    elif speech_state == HOST_PLUS_GUEST:
        target_video_state = STATE_HOST_GUEST_OVERLAP
    elif speech_state == GROUP_OVERLAP:
        target_video_state = STATE_GROUP_OVERLAP
    else:
        target_video_state = STATE_IDLE_WIDE

    stable_video_state = apply_video_hysteresis_and_cooldown(
        current_state=current_video_state,
        target_state=target_video_state,
        shot_hold_time=1.2,
        cooldown=0.7,
        overlap_debounce=0.12,
        silence_timeout=0.8,
    )

    if stable_video_state == STATE_HOST_FOCUS:
        output_camera = CAM_4
    elif stable_video_state == STATE_GUEST_CLOSE:
        output_camera = CAM_3
    elif stable_video_state == STATE_GUEST_SAFE:
        output_camera = CAM_2
    elif stable_video_state == STATE_MULTI_GUEST:
        output_camera = CAM_2
    elif stable_video_state in (STATE_HOST_GUEST_OVERLAP, STATE_GROUP_OVERLAP, STATE_IDLE_WIDE):
        output_camera = CAM_1

    if should_insert_reestablishing_wide():
        output_camera = CAM_1

    audio_levels = compute_audio_mix(
        active_set=active_set,
        recently_active_window_ms=350,
        attenuation_db=-18,
        standby_db=-9,
        hard_mute_db=-96,
        hard_mute_timeout_s=2.0,
        pre_roll_ms=300,
        post_roll_ms=120,
    )

    emit_video_cut_if_needed(output_camera)
    emit_audio_gain_updates(audio_levels)
    current_video_state = stable_video_state
```

## 13. Acceptance criteria

Система считается реализованной корректно, если одновременно выполняются все критерии ниже.

### 13.1 По видео

- Если говорит только ведущий, в эфире `CAM_4` не позже чем через `700 ms` после подтверждения речи.
- Если говорит один гость и его реплика длиннее `3 s`, в эфир сначала выходит `CAM_2`, затем `CAM_3`, если она успела навестись.
- Если камера 3 не успела навестись, в эфире не появляется moving-shot; вместо этого остаётся `CAM_2`.
- Если одновременно говорят минимум два гостя, система удерживает `CAM_2`.
- Если одновременно говорят ведущий и гость, система удерживает `CAM_1`.
- На паузе длиннее `800 ms` система переходит на `CAM_1`.
- В быстрых обменах `ведущий ↔ гость` монтаж не делает cut чаще, чем раз в `700 ms`, кроме допускаемых приоритетных переходов из safe-plan.

### 13.2 По звуку

- Начало реплики не обрезается при срабатывании VAD за счёт `audio_pre_roll`.
- При одиночной речи активный микрофон звучит на `0 dB`, молчащие каналы не мешают и не накапливают заметную протечку.
- При overlap двух и более говорящих система не глушит реального второго спикера.
- При ложном overlap из-за bleed система не открывает лишний микрофон на полный уровень.
- Закрытие канала не создаёт заметных щелчков и резких скачков громкости.

### 13.3 По устойчивости

- Система корректно отрабатывает минимум следующие сценарии:
  - говорит ведущий;
  - говорит один гость;
  - говорят два или более гостя одновременно;
  - короткая реплика гостя;
  - быстрый обмен репликами `ведущий ↔ гость`;
  - пауза;
  - камера 3 ещё не навелась;
  - говорящий уже замолчал, пока камера 3 переводилась.

## 14. MVP и расширения второй очереди

### 14.1 MVP

В MVP обязательно входят:

- детекция речи по 4 аудиоканалам;
- bleed suppression по относительному доминированию;
- state machine из раздела 10;
- safe-plan для камеры 3;
- `CAM_1 / CAM_2 / CAM_3 / CAM_4` по правилам данного документа;
- аудио attenuation + hard mute + pre-roll;
- логирование всех видеосостояний, активного набора участников и состояния камеры 3.

### 14.2 Вторая очередь

Во вторую очередь допускается добавить:

- учёт лиц и трекинга на видео как дополнительный модификатор уверенности;
- отдельный прогноз длины реплики на основе истории участника;
- адаптацию порогов под конкретную студию;
- операторский semi-auto режим с подсказкой рекомендуемой камеры;
- персональные профили гостей по чувствительности микрофона;
- автоматическую коррекцию частоты re-establishing shot по темпу разговора.

### 14.3 Что не входит в MVP

Следующие задачи не входят в первую поставку:

- ручной GUI для редактирования всех state transitions;
- обучение ML-модели на разметке конкретного шоу;
- автоматический выбор композиции внутри кадра камеры 3;
- полноценный vision-only fallback без аудио.
